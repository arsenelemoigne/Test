================================================================================================
1. THE CHALLENGE AND HOW IT IS SCORED
================================================================================================
BottleCapAI ThinkingCap Test (github.com/BottleCapAI/ThinkingCap-Test).
Goal: make Qwen3-0.6B (a 0.6-billion-parameter model that "thinks out loud" before answering)
write fewer tokens, thinking included, while keeping its accuracy.
Our own limit: accuracy change of at least -3 points against the untouched model.

Rules that matter here:
  - Start from Qwen3-0.6B; LoRA adapters or changed weights are allowed.
  - The model must load in plain Transformers and vLLM, no custom code.
  - The model must still think before it answers (thinking may not be switched off).
  - No training on the evaluation benchmarks.
  - Evaluation settings stay unchanged: prompt, sampling, token caps (4,096 tokens; 8,192 for code).
  - Answers cut off by the token cap count as wrong.
  - The organisers value original ideas ("not how well you can copy others").

The four benchmarks, each worth 25% of the score:
  SVAMP   math word problems, 1,000 questions
  MBPP+   writing Python functions, 378 questions
  BFCL    function calling, 840 questions in 3 parts:
            simple_python (one function offered, 400), multiple (several offered, 200),
            irrelevance (no offered function fits; the right answer is to call nothing, 240)
  IFEval  following formatting instructions ("3 paragraphs, no commas"), 541 questions

Scoring:
  Tokens saved     = 1 - geometric mean of the per-benchmark token ratios (new tokens / old tokens),
                     with BFCL's three parts pooled into one benchmark. Each benchmark counts equally,
                     so the long code answers do not dominate.
  Accuracy change  = plain average of the four per-benchmark accuracy changes.
Full evaluation = 2,759 questions x 8 answers each. We use a 240-question subset (the first 40
questions of each of the 6 parts, in the evaluation's own fixed order), 4 answers each, sometimes 8.


================================================================================================
2. THE METHOD
================================================================================================
2.1 What a run does, step by step
  1. Practice questions (never test questions) are answered by the untouched model, 2 answers each,
     with the evaluation's own sampling settings and token caps.
  2. Answers are graded with the evaluation's own graders. Wrong answers are thrown away.
  3. Each correct answer is (or is not, for the "uncut" control) trimmed by the MVT rule.
  4. Safety check: the model must reach the right answer twice, answering naturally from the trimmed
     thinking. If it fails, the original uncut answer is kept for that question instead.
  5. Per question, the shortest accepted answer becomes a training example.
  6. A small add-on (LoRA, rank 16, about 10 million numbers, 1.7% of the model) is trained on these
     examples: 2 passes over the data, learning rate 1e-4, 16 examples per step. The 600 million
     numbers of the model itself are frozen. The model learns to write like the examples.
  7. The untouched model plus that add-on takes the test: the 240 questions, 4 answers each, all four
     benchmarks. Result = tokens saved and accuracy change against the untouched model.
  Every run starts fresh from the untouched model: 25 separate add-ons, not stacked.
  Each run trains on ONE task type but is tested on ALL four benchmarks, so we see both the effect
  on its own task and the side effects (spill-over) on the others.

2.2 What MVT is (the cut rule)
  For each correct answer, we stop the model after every piece of its thinking and measure, by
  teacher forcing, how likely it is to write its own correct final answer from that point.
  That gives a confidence curve, e.g. 20% -> 60% -> 95% -> 96% -> 96%.
  The Marginal Value Theorem (Charnov 1976, foraging theory: a bird leaves a berry bush when the
  berries come slower than its average rate, counting the trip to the next bush) says: stop at the
  first point where no later part of the thinking pays better per token than the average so far,
  g(t) / (t + c). The "travel cost" c is patience:
      c = 1024  "patient":   stays longer, cuts less
      c = 256   "impatient": stops sooner, cuts more
  A "piece" can be:
      a paragraph                      (the "paragraphs" runs)
      a fixed batch of 32 tokens       (the "32-token" runs; can cut in the middle of a sentence)
  After the cut, pieces before the cut point that added no confidence are also tried for removal,
  kept out only if the confidence holds.
  MVT is only used to prepare training examples. At test time the model works alone; it has simply
  learned, by imitation, to think about as long as the trimmed examples.

2.3 What "uncut" (whole) means
  The same questions, the same correct answers, no trimming (only the shorter of two correct answers
  is chosen). It measures what training on that kind of data does by itself, so that each cut run
  can be compared to it and not only to the untouched model.

2.4 Reading the numbers
  "X% / Y" = answers X% shorter (negative = longer) / accuracy changed by Y points.
  Noise: with 40 questions x 4 answers per benchmark part, one benchmark cell moves by about
  +/-4 points by chance (the confidence intervals on single benchmarks are +/-5 to +/-9 points).
  Averages and patterns repeated across runs are more reliable than any single cell.

  300 questions per source, 2 answers each, token caps 4,096 (8,192 for code). Seed 0.

3.2 Fix made before the run: ToolACE "no function fits" examples
  About half of ToolACE's prose replies (no call) were really "a fitting function exists but a
  required argument is missing, please provide it". BFCL's irrelevance tests something else: no
  offered function fits at all. Training on the clarification cases could teach the model not to
  call when it should. prepare_types.py now keeps a prose reply as "no function fits" only if it says
  the functions cannot do it ("none of", "do not", "cannot", ...) and does not name a function or
  ask for a missing/required argument. Checked on CPU before the GPU run:
      5,025 one-function, 3,615 several-function, 276 genuine "no function fits" examples usable;
      300 kept: 144 / 72 / 84.
  (The mvt-fading session's "shortest of 8" data was built before this filter.)

3.3 What changed from night 1 (branch mvt-fading, "Track 2b")
  - Practice data matched to the test (night 1: all of GSM8K, much harder than SVAMP; Hermes tool
    data; same IFEval-like data; old MBPP filter).
  - Token caps as the evaluation (night 1: 2,048 for all practice answers).
  - Both patience settings and both cut units for every type (night 1: mostly patient, paragraphs).
  - Multiple choice as its own type.
  - Same MVT code, same safety check, same training settings, same 240 test questions.

================================================================================================
11. WHAT WE LEARNED
================================================================================================
1. Matched practice data makes training itself free. All five uncut runs: -1.1 to +0.9 points.
   Night 1's data cost 2-3.5 points before any cut. The cost of a cut is now clearly the cut's own.
2. The right cut unit depends on how the type thinks:
     tool calls, instructions: short, well-paragraphed thinking -> paragraphs;
     code: one long plan -> paragraph cuts are all-or-nothing -> 32-token pieces;
     math: every step carries the calculation -> keep whole.
3. Patient vs impatient: on the trained task, about the same; impatient spreads brevity (and damage)
   further to other tasks.
4. Code is hurt by every cut, whatever task is trained (-2 to -14 points across 20 cut runs). The
   "think less" habit reaches code even from tool or instruction cuts. Code is the main weakness.
5. Instructions improve with every cut (+4 to +6, sometimes more): less overthinking helps IFEval.
6. Easy examples (multiple choice) teach "barely think" and break math everywhere: they need whole
   math beside them.
7. The harder the cut in training, the more spill-over, and past a point the model gets sloppier
   rather than shorter (deep 32-token cuts give little saving and real losses).
8. Easy, SVAMP-like math makes math cuts much less harmful than on all of GSM8K (-1 to -7 vs -16),
   but the filter leaves only 60 examples.
9. Combining adds up: the best combined model saves more than any single run, and its losses on
   code and math are close to the sum of what each cut does to them.
10. 8 answers settle results 1-4 points lower in saving than 4 answers for the best runs (selection
   effect + less luck).

12. SIDE INVESTIGATION: WHY NIGHT 1's TOOL RUN SHORTENED CODE BY 68% (AND TONIGHT'S BY 2%)
================================================================================================
Fact: night 1, training only on tool calls with the same MVT cut made code 68% shorter (-8.7);
tonight, code 2% shorter (-3.1).
Checked:
  - Same test (same 240 questions; the untouched model scores identically).
  - Same code for cutting, checking and training (git diff of prune_traces.py, sft.py, check_vllm.py
    between night 1's commit 3546e14 and now: only an added math filter and the token-cap change).
  - Token cap: 2,048 then vs 4,096 now; irrelevant for tool calls (2% capped then).
  - Only real difference: the practice data (Hermes then, ToolACE now).
Night 1 table: every training on Hermes tool data hurt code by 7.5-10 points, including the uncut
one (-9.4). Tonight the uncut ToolACE run: +0.6.
  night 1 (Hermes)          code: shorter / accuracy     tonight (ToolACE)    code
  uncut                     -1% / -9.4                   uncut                +6% / +0.6
  MVT patient paragraphs    +68% / -8.7                  MVT patient par.     +2% / -3.1
  MVT patient 32-token      +12% / -7.5                  MVT impatient par.   +30% / -4.4
  fading round 3            +57% / -10.0
  word scoring              +34% / -10.0
  Effect of the cut itself (vs uncut): night 1 code 68% shorter at +0.7; tonight 2% shorter at -3.7.
Mechanism: the add-on is shared by all tasks; the moment the model decides "done thinking" works the
same way for every question, so "stop sooner" learned on tool calls applies to code (code has the
most thinking to lose).
Best guess for the difference (untested): Hermes questions were easier (25% made-up "no fit" pairs:
an unrelated question paired with functions from another topic, obvious at a glance) and the model
thought longer on them (476 vs 265 tokens), so MVT removed about 130 tokens per example (44%) vs 60
(30%) tonight: a much stronger "think less" lesson that spread everywhere — the same mechanism as
easy multiple choice. A control run (Hermes data with tonight's settings) was queued, then removed
at the user's request.
Consequence: night 1's 42% average for that run was inflated by the code side effect; on tool calls
themselves both nights are equal.

13. COMPARISON WITH THE PUBLIC ENTRY "LIGHTNING McQWEN3"
================================================================================================
Source: blog.basta.one/blog/thinkingcap (14 Oct 2026) and github.com/basta/lightning-mcqwen3.
Author: Ondrej Bastar (GitHub "basta"), master's student at CTU Prague (AI and robotics; interests
interpretability and inverse RL), as presented on his own sites. Compute: RTX 4070 SUPER (12 GB) +
the Czech national grid (MetaCentrum).

His results (8 answers, self-reported; number of questions not stated):
  with a "think gate"     47.3% / -0.88   (stitched: gated BFCL run + ungated others;
                                           a full gated rerun gave 46.6% / -1.33)
  without the gate        43.2% / -0.85   <- the fair number
  per benchmark (no gate): SVAMP 66% / -3.8 · MBPP+ 39% / -1.9 · IFEval 32% / +1.4 · BFCL 25% / +0.9
The gate forces an empty thinking block on ~30% of BFCL prompts from the evaluation script (not the
weights): very probably against the rules (the model must think before answering; thinking may not be
turned off; evaluation settings unchanged; shortening must be in the model). He does not discuss it.

His recipe:
  1. Chain-of-Draft distillation: answers written under "max 5 words per thinking step" with two
     examples; prompt removed; SFT on 11,247 correct traces (LoRA r16, lr 1e-4, 1 epoch) -> 26.5% / -1.27.
  2+3. On-policy cut oracle on the distilled model: 9.3k new questions x 4; cuts at the sentence ends
     nearest 10%..90% of the thinking; 4 re-answers per cut, safe only if 4/4 right (197k cuts);
     DPO pairs (9,034): 40% "safe short > full", 40% "safe > too early (wrong)", 20% hard;
     lr 2e-5, beta 0.1, stopped at step 100 of 561 -> 42.5% / -1.45.
  4. Math correctness DPO with an NLL anchor (732 pairs) -> 43.2% / -0.85.
  Proof that on-policy matters: the same oracle on the untouched model gave 11.4% (SFT) / 28.1% (DPO).
  Failures he reports: naive DPO shortest-vs-longest 90% / -27; correctness DPO without anchor
  -5.2 (validation); more SFT no gain; LoRA merge 51.0% / -3.93 (2 answers); gating math/code;
  another model's traces (distribution shift).
  Side effects he reports: more agreement with user errors (Sydney as capital 6/6; 9.11 > 9.9 6/6),
  more invented details. Training data: GSM8K, Skywork, ARC-Easy, CommonsenseQA (+ ToolACE for the gate).
  Credits: Chain-of-Draft, ThoughtFold, ThinkSwitcher, RPO.

Side by side:
                         ours (codecut, 8 ans, 240 q)   his (no gate)      our night-1 best
  overall                44.3% / -1.6                   43.2% / -0.85      37.1% / -0.6
  tool calls (BFCL)      42-51% / about 0               25% / +0.9
  instructions (IFEval)  20% / +5.0                     32% / +1.4
  code (MBPP+)           73% / -7.2                     39% / -1.9
  math (SVAMP)           15% / -4.1                     66% / -3.8
Reading:
  - Savings level (one point apart, inside our 39-50% interval); he loses about half as much accuracy.
  - We are far ahead on tool calls; he is ahead on instructions and, clearly, on math.
  - Code: he took a moderate 39% at small cost; our cut overshoots (73%) and costs 7.2.
  - Math: he keeps every step but writes each tersely (in the model's own words); MVT removes steps.
  - His closest experiment to ours (one round of cuts on the untouched model, SFT) gave 11.4% / -0.34;
    our per-type runs give 15-26% on the trained task: same family, slightly better.
  - Our selection of the best of 3 combinations on the same 240 questions flatters our number a bit.
Lessons worth taking (with credit): cut the CURRENT model's answers in rounds; show "too early"
examples, not only good short ones; verify cuts more strictly (4/4 vs our 2/2); terse rewriting for
math; stop training early and keep checkpoints; check behaviour outside the benchmarks.
Our own contribution: MVT picks one cut point per answer (he tries 9, far more compute); per-type
handling and the spill-over map; keeping math whole.

14. LIMITS AND CAVEATS
================================================================================================
- 240 questions (40 per benchmark part), 4 answers per run (8 for rechecks): a development signal,
  not the leaderboard. One benchmark cell moves by about +/-4 points by chance; intervals on single
  benchmarks are +/-5 to +/-9 points.
- The 8-answer rechecks reuse the first 4 answers' seeds (same generations for the first 4).
- The best combined model was chosen among 3 on the same questions it is reported on.
- Each run was trained once: training randomness (night 1: a retrain moved a result by ~2 points
  and several % of saving) is not measured.
- Math training used only 60 examples (strict "easy" filter).
- No full evaluation; no check of behaviour outside the benchmarks (agreement with wrong user
  statements, invented details).
- The "+5 to +13" IFEval gains in several runs are probably partly luck (they shrink with 8 answers).

APPENDIX A. GLOSSARY
================================================================================================
add-on / LoRA      small trainable layers on top of the frozen model (rank 16, ~10M numbers)
answer / trace     the model's full reply: thinking (<think>...</think>) + final answer
patient / c=1024   MVT travel cost 1024: stays longer, cuts less
impatient / c=256  MVT travel cost 256: stops sooner, cuts more
paragraphs         cut points at paragraph breaks
32-token pieces    cut points every 32 tokens (can fall mid-sentence)
uncut / whole      trained on correct answers without trimming (the control)
spill-over         effect of training one task on the other tasks
4 answers / 8 ans  number of sampled answers per test question (more = less luck)
s4-base / s8-base  the untouched model's scores with 4 / 8 answers
geometric mean     the challenge's way of averaging token ratios so each benchmark counts equally
